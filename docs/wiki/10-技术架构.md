# 系统地图

## 一句话理解

`stock-center` 采用新的 `python-back` 作为后端核心，第一阶段只迁移行情与数据引擎。旧 `stock-analysis` 是参考源，不再承载新架构实现。

## 分层

| 层 | 责任 |
| --- | --- |
| API | FastAPI 暴露 `/api/v1/market-data/query/*`。 |
| Query Service | `MarketDataQueryService` 统一 `query_mode`、`engine_priority`、fallback、raw landing 和 canonical upsert。 |
| Sync Service | `MarketDataSyncService` 负责批量同步板块目录、成分股和股票基础资料，并输出任务摘要。 |
| Capability Registry | 登记每类数据的分类、主源、fallback、目标表和是否可生成指标。 |
| Provider | `AkShareProvider`、`MootdxProvider` 只负责外部源调用和字段初步映射。 |
| Repository | 读写 Raw、Canonical、Derived 三层 `t_` 表。 |
| Config Center | `ConfigCenterService` 管理 Search、LLM、Notification 的固定配置对象、敏感值池和非敏感参数。 |
| LLM Runtime | `LlmRuntimeService` 作为内部服务调用 OpenAI-compatible 模型，并基于本地服务构建固定上下文包。 |
| Skill Runtime | `SkillRuntimeService` 作为内部服务运行项目内 Skill 资源，支持 family 级 Key 注入和 capability fallback。 |
| Scheduler Center | `SchedulerRuntime` 和 `SchedulerService` 管理任务定义、APScheduler 注册、手动触发和运行日志；具体业务任务通过 `JobHandlerRegistry` 后续逐步接入。 |
| Data Assets | `DataAssetsService` 只读巡检核心数据资产、最新日期、最近任务状态和索引缺口，支撑数据中心页面。 |
| Realtime Market | `RealtimeMarketService` 按交易日历和盘中时段维护 TickFlow 全市场 Quote、MooTDX 优先分钟线、板块强度和股票池实时缓存；从完整 Quote 轮次派生市场宽度、日内结构、可验证涨跌停、排行、概念热度、排名变化和短期事件流，并用最近已收盘日的日频 MA 作为只读趋势参照。它还只读日频涨跌停事件生成连板梯队与炸板结构：先检查 Raw 完成标记，避免把零行误判为无事件。结果通过 Redis/内存与 SSE/API 供页面复用。 |
| Stock Pool Center | `StockPoolService` 管理系统池、自定义池、股票代码成员关系和一对一实时策略；详情只读 `t_stock`、`t_sector_basic/t_sector_component`，不触发外部 Provider。 |
| Strategy Center | `StrategyCenterService` 管理策略草稿、专属动态策略池、收盘候选与模拟交易审计数据；当前没有 evaluator、实时确认或券商连接，因此定义不能直接启用。 |
| Web Admin | `web-admin` 提供 Vue3 管理后台，一级入口包含系统设置中心、数据中心、实时市场总览、每日盘后报告、情绪模型、策略中心、调度任务、板块中心、股票池和个股行情。 |
| Database | raw/canonical/derived 三层数据资产。 |

## 数据原则

数据库是第一优先资产。Provider 是补齐和刷新手段。所有外部响应先有 raw landing，再决定是否写入 canonical 表。

## 配置原则

Search、LLM、Notification 和数据源密钥统一走配置中心 v2。配置中心使用 `t_system_config` 表达固定配置对象，使用 `t_config_value` 管理 API Key、Webhook、Token、Password 等敏感值池，使用 `t_config_option` 管理非敏感参数。实时 Quote 的 TickFlow API Key 由 `market_data/tickflow` 管理；MooTDX 分钟线不需要密钥。Skill 本体不进入配置中心，但 Skill Runtime 会复用 `search` 分类下的 family 级 Key 池。

LLM 第一版只作为内部 Python service，不暴露 `/api/v1/llm`。模型分析所需额外数据由后端调用本地服务组装为固定上下文包，模型不能主动访问本地服务或公网。

Skill Runtime 第一版也只作为内部 Python service，不暴露 `/api/v1/skills`。它负责执行旧项目迁移来的 Skill 资源和 fallback 链，不承载具体业务分析。

Scheduler Center 只实现调度底座，不承载业务逻辑。`t_scheduler_job` 保存任务定义，`t_scheduler_job_run` 保存运行日志；只有启用且配置 `cron_expr` 的任务会被 APScheduler 注册，`cron_expr=null` 表示仅手动运行。当前已由行情模块接入 `sync_sector_catalog` 和 `sync_stock_basic` 两个默认 disabled 的同步任务，策略扫描、通知发送等任务后续按模块通过 `JobHandlerRegistry` 接入。

Web Admin 当前实现系统设置中心、数据中心、实时市场总览、每日盘后报告、情绪模型、策略中心、调度任务、板块中心、板块资金大屏、股票池和个股行情工作台。数据中心通过 `/api/v1/data-assets/summary` 只读巡检核心表行数、最新日期/时间、最近任务状态、索引缺口和覆盖率；通过 `/api/v1/data-assets/assets/{asset_code}/gaps` 下钻个股资产缺口，区分真实缺失和当日停牌解释；通过 `/api/v1/data-assets/realtime-health` 与 `/api/v1/realtime/market-overview` 展示实时行情状态和同轮市场总览。独立的 `/market-overview` 页面只读同一缓存轮次，展示概念题材、申万行业、股票池、盘中宽度轨迹、可验证涨跌停、日内结构、涨跌/成交额/成交量榜和短期变化事件；实时价相对 MA5/20/60 的比较严格使用最近已收盘日的 `system:daily_close` 因子并标注参照日。独立的 `/post-close-market` 页面按同一事实日读取连板梯队、炸板事件、V1 兼容情绪、V2 双分/周期、概念热度、龙头和涨停关联证据；任一完成门槛不足时明确显示待完成。`/emotion-models` 只管理模型草稿、校准和显式启用，页面不直连 Provider。`/strategies` 只管理研究草稿、候选/模拟交易审计模型和专属动态策略池；当前没有 evaluator，不能启用策略或生成交易。股票池通过 `/api/v1/stock-pools` 管理系统池和自定义池；成员只关联 Canonical `stock_code`，并可通过实时策略决定 Quote/分钟线资源归属。

`MarketSentimentService`、`MarketDailyReviewService` 与 `MarketEmotionService` 位于盘后 Derived 层：22:15 的 `calculate_market_daily_sentiment` 先从 `t_daily_bar/t_stock_fund_flow_daily/t_limit_event_daily/t_sector_component/t_trade_calendar/t_provider_raw_record` 计算 V1 `t_market_sentiment_daily`、`t_market_sector_heat_daily` 和 `t_market_limit_up_evidence_daily`，再在存在 active V2 模型时写 `t_market_emotion_daily`。V2 使用滚动历史分位数给出“短线接力情绪分”和“大盘风险偏好分”，并保留每项输入、分位、贡献和阶段证据；模型参数位于 `t_market_emotion_model`，历史版本不覆盖。21:30 的 `daily_close_enrichment_ingest` 还会写入 `t_market_north_flow_daily`（`moneyflow_hsgt`，保留 Provider 原始单位）；`hk_hold` 与 `margin` 只滚动补最近 5 个实际披露日，作为 V2 延迟辅助确认，不进入同日核心分数也不阻塞报告。V2 基线校准复用 22:15 handler 的手动 `emotion_mode=baseline`，每 20 个交易日写一批；日常 V2 计算不产生外部调用。概念热度直接由成分股事实聚合，不依赖可能延迟的 `ths_daily`；龙虎榜、概念归属和已入库公告只记录关联证据，不构成涨停因果结论。LLM 只能在后续作为该事实的解释层，不能改写评分或证据。

## 量化数据分类

| 分类 | 代表数据 | 说明 |
| --- | --- | --- |
| 基础事实 | 股票、板块、概念、行业、指数、成分股 | 用于关联、筛选和归属，不直接等同指标。 |
| 行情事实 | 日线、分钟线、quote、盘口、分笔、板块行情、指数行情 | 用于展示、刷新和派生价格/成交量指标。 |
| 事件事实 | 龙虎榜、公告、资金流、融资融券、涨跌停池 | 先保存为可查询事实，再派生事件指标。 |
| 量化指标 | 技术指标、资金流指标、龙虎榜指标、板块强度、相对强弱 | 从 canonical 层计算，可重建，但迁移旧结果必须保留来源。 |

每日量化沉淀由三段任务组成：`daily_close_core_ingest` 负责 18:00 已稳定的日线、daily basic、资金流、核心指数与基础因子，`daily_close_enrichment_ingest` 负责 21:30 才更可靠的涨跌停/炸板、停复牌、板块日线和其他增强事实/因子，`daily_close_repair_ingest` 负责次日滚动补缺。核心阶段的七个当日指数日 K 由 TickFlow 单指数 `klines` 优先获取，只有当日 bar 缺失才回退 Tushare；其余日频事实和历史指数回填仍遵循 Tushare canonical 链路。策略评估、市场状态、市场情绪、LLM 和 Skill 仍保持在后续独立任务中。

历史初始化与每日沉淀分离。历史入口收敛为个股、板块、指数各一条日频事实任务和一条日频因子任务，固定按 `stock facts -> stock factors -> sector facts -> sector factors -> index facts -> index factors` 执行。历史分钟线/分钟因子不在初始化范围；个股和指数因子使用 PostgreSQL 集合计算，板块因子仅以受控日期 worker 并行。完整表关系、并发依据和运维参数见 [[历史数据资产初始化]]。
