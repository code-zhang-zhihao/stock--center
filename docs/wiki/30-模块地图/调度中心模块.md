# 调度中心模块
<!-- wiki-migration -->

## 定位

`scheduler_center` 是 `stock-center` 的调度底座。它负责任务定义、任务触发、APScheduler 注册、运行日志和基础状态查询，不承载具体行情同步、策略扫描、通知发送等业务逻辑。

旧 `stock-analysis` 的调度模块可参考运行时设计，但不能照搬 `SchedulerApplicationService` 的业务耦合方式。新项目中，具体任务必须通过 `JobHandlerRegistry` 注册 handler 后才能执行。

## Runtime 规则

- `SCHEDULER_ENABLED=false` 为默认值，服务启动时不会自动注册任务。
- `SCHEDULER_ENABLED=true` 时，后端启动会尝试启动 APScheduler 并从数据库 reload 任务；如果数据库连接失败，FastAPI 仍继续启动，调度器关闭并在 `/api/v1/scheduler/status.error` 暴露错误摘要。
- `SCHEDULER_MAX_CONCURRENT_JOBS=2` 控制全局任务并发。
- 默认时区是 `Asia/Shanghai`。
- 第一阶段只支持五段 cron。
- `cron_expr=null` 表示仅手动运行。
- cron 星期语义按 crontab 处理：`1-5` 表示周一到周五，注册 APScheduler 前会转换，避免星期偏移。
- 任务配置页面固定使用 `Asia/Shanghai`，支持仅手动、每天、每周、每月 1-28 日和自定义五段 Cron；后端会在写库前校验 Cron，非法值返回 `invalid_cron_expr`。
- `timeout_seconds` 表示单次 handler 尝试的超时秒数；失败后最多按 `retry_count` 重试，并在每次尝试间等待 `retry_interval_seconds`。
- 默认 payload 与手动运行 payload 都按 `parameter_schema` 校验必填、类型、范围和枚举；schema 未定义的新字段会被拒绝，已有历史扩展字段可保留。
- 执行前使用 PostgreSQL advisory lock 做轻量防重复保护；拿不到锁时记录 `skipped/already_running`。
- 手动触发的异步任务由 `SchedulerRuntime` 持有当前进程内的 active task。前端可调用 `POST /runs/{run_id}/cancel` 请求终止；取消是协作式的，已经提交的批次数据保留，运行记录会尽量标记为 `cancelled/job_cancelled`。
- 后端启动时会清理上次进程退出遗留的 `running` 记录，将其标记为 `failed/scheduler_orphaned_after_restart`。这只修复运行日志状态，不回滚已经提交的业务数据。
- 任务完成后写入 `t_scheduler_job_run` 状态时，如果当前数据库连接已经被云库重启、恢复或网络中断关闭，调度中心会回滚当前 session，并用新 session 重试一次状态写入。这样可以避免“业务数据已经提交成功，但运行记录因为坏连接被误标失败”的情况。
- 任务执行会输出 `INFO` 级别日志：开始、重试、成功、跳过、关键 payload keys 和 affected rows。
- 业务模块必须输出自己的 `INFO/WARNING` 日志：长流程至少覆盖阶段开始、输入规模、批次完成、缺失数据摘要和最终行数。失败详情或关键缺失数量应进入 `t_scheduler_job_run.result_summary`，便于前端运行详情和日志共同排查。
- `t_scheduler_job_run.result_summary` 写入前会统一做 JSON-safe 编码；业务 handler 返回 Pydantic 结果时应使用 `model_dump(mode="json")`，避免 `date`、`datetime`、`Decimal` 等 Python 对象导致 JSONB 入库失败。

## API

所有接口都在：

```text
/api/v1/scheduler
```

主要能力：

- `/jobs?tag_code={tag_code}`：按标签查看任务定义；省略标签时返回全部任务。
- `/tags`：读取启用标签及各标签下的任务数，供页面渲染筛选器。
- `/jobs`：创建、更新、删除任务定义。
- `PATCH /jobs/{job_code}`：更新任务排期、启停、默认 payload、单次尝试超时和重试策略；更新成功后 API 自动 reload Scheduler。
- `/jobs/{job_code}/pause` 和 `/jobs/{job_code}/resume`：暂停或恢复任务。
- `/jobs/{job_code}/run`：手动触发任务。
- `/runs` 和 `/runs/{run_id}`：查询运行日志。
- `POST /runs/{run_id}/cancel`：终止当前进程内仍在运行的任务；如果运行记录为 `running` 但当前进程没有 active task，会标记为 `cancelled/job_cancelled_not_active`。
- `/status` 和 `/reload`：查看调度器状态和重新加载 cron。
- `/db-pool/status`：查看数据库连接池状态。

数据库连接诊断：

- `/api/v1/health` 只表示后端进程存活，不代表数据库可用。
- `/api/v1/health/db` 执行只读 `select 1`，返回 `ok/failed`、错误类型、错误摘要和连接池状态。
- `python-back/scripts/check_database_connection.py` 会用 `DATABASE_SSL=auto/disable/require` 三种模式探测当前 `DATABASE_URL`，输出脱敏连接目标和推荐排查方向。
- `DATABASE_CONNECT_TIMEOUT_SECONDS` 控制 asyncpg 连接超时；`DATABASE_SSL` 支持 `auto`、`disable`、`require`。

基础同步任务默认 `retry_count=0`，便于手动验证时快速暴露外部源失败；需要生产重试策略时再显式调整。`sync_trade_calendar` 默认同步当前年份，也可通过 payload 指定 `year` 和 `upsert/rebuild`；它沿用旧项目规则：周一到周五且 `chinese_calendar.is_workday(date)` 为真即开市，并补齐前后交易日。`sync_sector_catalog` 使用当前快照语义：只有单板块成分源确认完整时才物理删除缺失关联。其同花顺分页源由 Provider 内部逐页校验并重试，失败板块不写入部分结果。

`sync_stock_basic` 的状态口径固定为：沪深 Tushare `stock_basic.list_status=L/P/D` 分别对应 `active/suspended/delisted`；北交所/BJ/BSE 以及 `4/8/920` 代码段统一为 `excluded`，不进入股票池候选、`all_a_share` 动态范围和每日沉淀。任务每次按 `stock_code` Upsert；名称匹配 `退市*`、`*退`、`*(退)`、`*（退）` 时，即使 Provider 暂时仍返回 `L`，也会直接更新为 `delisted`，不需要单独执行修复 SQL。AkShare/MooTDX fallback 只补充沪深 active 列表，不覆盖已有 `excluded/delisted/suspended` 状态。状态同步不删除自定义 `t_stock_pool_member`，板块成分仍由 `sync_sector_catalog` 独立维护。

`sync_index_catalog` 独立维护指数主数据，不与每日 `index_daily/index_dailybasic` 沉淀混在一起。它默认同步核心指数基础资料，并只对成分型指数同步当前成分股主数据。指数成分不保留历史快照；同步某指数时，本次完整结果中不存在的旧成分会被物理删除。Tushare 是主源；`index_weight` 默认按 `weight_lookback_months=3` 查询最近 3 个自然月，然后按 `trade_date` 分组取最新且满足预期成分数量的完整结果。AkShare fallback 只用于补充基础/成分，最终 canonical `index_code` 仍使用无后缀代码。成分型指数会校验预期成分数，fallback 去重后明显不足时跳过入库和删除。

标签初始映射为：六条 `backfill_*` 日频任务归入“历史”；四级收盘流水线、`calculate_market_daily_sentiment` 和数据资产健康缓存归入“每日”；交易日历、股票、板块、指数同步归入“主数据”。“策略”标签先保留为空，待策略调度任务落地后直接写入关联表即可。

`scheduler_noop`、`sync_tushare_a_share_topic` 与旧 `daily_market_close_ingest` 已从当前任务定义和 handler 注册中移除。每日沉淀固定使用分钟、核心、增强、缺口修复四级任务；历史补数仍使用独立 `backfill_*` 任务。删除定义不会删除 `t_scheduler_job_run` 历史记录。

`daily_close_minute_ingest` 默认 cron 为 `30 15 * * 1-5`。MooTDX 默认 10 个独立连接并行拉取；网络读取与数据库写入通过有界队列重叠。分钟线写完后，`t_stock_factor_minute` 按默认 200 只股票、每片约 4.8 万行执行 PostgreSQL 窗口计算和独立提交，分片范围可配置为 50–500。`append_safe` 会跳过已完整的分钟线和分钟因子；覆盖率达到 95% 后，分钟线与分钟因子共同保留最近 30 个交易日。

`daily_close_core_ingest` 默认 cron 为 `0 18 * * 1-5`，单次超时 2 小时、失败最多重试 1 次且间隔 300 秒。核心阶段不再获取分钟线，仅并行沉淀日线、daily basic、个股资金流和核心指数，再集合计算日频基础因子与技术快照。七个核心指数优先由 TickFlow 单指数未复权日 K 获取，只有目标交易日缺失才回退 Tushare。涨跌停/炸板、停复牌和板块日线不再作为 18:00 的完整性前置，统一延后到增强阶段。

`daily_close_enrichment_ingest` 默认 cron 为 `30 21 * * 1-5`。涨跌停/炸板与停复牌、板块日线、`stk_factor_pro`、龙虎榜、指数每日指标、市场统计和板块资金流在独立数据库 session 中受控并发执行；板块 `ths_daily` 按 500 个代码一批，首轮约 3 次请求并至多一次缺失批量重试。专业技术因子只合并到既有 `features.tushare_technical`，不再全市场重算基础 MA 和资金因子。`daily_info` 返回 0 时记录为 `deferred`，不使增强任务失败。此阶段缺失会使报告质量标记为 `degraded`，但不把 18:00 核心任务标为阻塞。并发仍受 Token 池、专属 endpoint、共享限流和 Scheduler timeout 约束。

`calculate_market_daily_sentiment` 默认 cron 为 `15 22 * * 1-5`，在增强事实之后仅查询本地 PostgreSQL。它要求 active 日线覆盖至少 95% 且 `limit_list_d` 对应 Raw 完成标记已存在；否则记录 `pending`，让盘后页显示等待原因。默认 `include_report_facts=true`，继续沉淀概念热度、前 24 个热点概念的龙头和涨停关联证据；关闭该参数时只回填情绪基线，适合大范围历史初始化。概念热度直接聚合成分股事实，不等待 `ths_daily`；同一算法版本按日期 Upsert，不改变 canonical 事实或其他算法版本。

`daily_close_repair_ingest` 默认 cron 为 `0 8 * * 1-5`，只检查最近 3 个已经存在 canonical 日线的交易日。任务读取核心/增强覆盖率和 Raw 完成标记，按日调用缺失的 `top_list/index_dailybasic` 等接口，并只重算受资金流、专业技术或板块输入影响的因子；没有缺口时直接 `skipped`。分钟数据不进入次日修复。

四级任务的结果摘要统一包含 `stage_timings`、`block_status`、`coverage`、`core_ready`、`report_quality` 和 `missing_blocks`。核心资产达到覆盖阈值后报告可生成；增强数据未齐时 `report_quality=degraded`，`daily_info` 等非阻塞项保留在缺失列表中。

历史回填不属于每日收盘沉淀。`docs/sql/55-data-asset-history-pipelines.sql` 将入口固定为个股、板块、指数各一条事实任务和一条因子任务，并删除旧的 7 条任务定义；`docs/sql/56-sector-history-range-backfill.sql` 将板块事实任务升级为逐板块区间请求和独立资金流窗口并发；`docs/sql/57-stock-history-limit-events.sql` 为个股事实任务增加按交易日查询的 `limit_list_d/suspend_d` 事件阶段。推荐顺序是 `stock facts -> stock factors -> sector facts -> sector factors -> index facts -> index factors`；全部任务默认 disabled、手动先行、支持 `append_safe/rebuild`。完整参数、落表、依赖、并发依据、分钟数据边界和 smoke 步骤见 [[历史数据资产初始化]]。

四级调度迁移由 `docs/sql/58-daily-close-four-stage-pipeline.sql` 提供；已运行过旧版本时，执行 `docs/sql/64-daily-close-late-facts-enrichment.sql` 迁移两个任务的默认 payload 后 reload Scheduler。两个脚本均不删除业务事实。`cyq_chips` 明细已从业务沉淀中移除；`cyq_perf` 也不再作为全市场批量沉淀来源。

## 第一阶段边界

- 不迁移旧项目 `scheduled_job` 里的具体业务任务。
- 前端调度任务页面支持按数据库标签筛选、展示任务标签，并支持编辑排期、执行策略和默认 payload；`parameter_schema` 驱动默认参数和手动运行表单，展示中文字段标签、说明、选项及数值范围。
- 不让调度模块直接 import 行情、LLM、Skill、通知等业务模块；这些模块各自提供 handler 并在应用启动时注册。
