## 当前边界

配置中心 v2 管理四类固定配置对象：

- `search`：问财、妙想、Kimi Search 的 Key 池。
- `llm`：固定 LLM 模型配置、默认模型和 Key 池。
- `notification`：飞书、邮箱、自定义 Webhook 的渠道参数。
- `market_data`：Tushare Pro、TickFlow、Redis Cache 和实时行情运行参数。

Skill 本体不进入配置中心；Skill Registry、Skill 参数和 Skill fallback 仍由 `skill_runtime` 代码注册表管理。Skill Runtime 只按固定 `search` 配置编码读取 Key。

## 表结构

| 表 | 说明 |
| --- | --- |
| `t_system_config` | 固定配置对象，例如 `iwencai_search`、`kimi_llm`、`aliyun_coding_plan`、`feishu`。 |
| `t_config_value` | 敏感值池，主要保存 Search、LLM、Tushare Token、TickFlow API Key 和 Redis URL；Tushare Token、TickFlow API Key 都可附带非敏感 `endpoint_url` 覆盖入口。 |
| `t_config_option` | 参数表，服务 LLM 和 Notification；Notification 的 `webhook_url`、`smtp_password`、`token` 也放这里。 |
| `t_runtime_call_log` | Search、LLM、Notification、Skill 等内部调用日志。 |

旧 `t_config_node`、`t_secret_key`、`t_config_relation` 已不再作为运行时来源；执行 `08-config-center-v2-rebuild.sql` 后会删除。

## 固定配置对象

Search：

```text
search

  miaoxiang_search
  kimi_search
```

LLM：

```text
llm
  kimi_llm
  kimi_llm_32k
  deepseek_chat
  aliyun_coding_plan
  volcengine_coding_plan
  openai_compatible
```

Notification：

```text
notification
  feishu
  email
  webhook
```

数据源：

```text
market_data
  tushare_pro
  tickflow
  redis_cache
  realtime_market
```

`is_default` 是分类级默认值。LLM 未指定 `config_code` 时读取 `llm` 分类默认项；Notification 后续如需要默认渠道也使用同一规则。

## Key 与敏感值规则

- Search、LLM、Tushare Pro Token 和 TickFlow API Key 写入 `t_config_value.encrypted_value`。
- Tushare 使用 `value_kind=token`，可配置多个 active Token，按 `priority/weight/last_used_at` 选择。限频 Token 进入 cooldown，无效 Token 标记 `invalid`，网络错误不会认定 Token 失效。
- Tushare Token 的 `endpoint_url` 可单独指定 API 入口；为空时回退该配置对象的 `api_url` option。Token、入口、优先级和状态作为同一条 `t_config_value` 一起轮换，避免 Token 与 URL 错配。
- `endpoint_url` 允许 `market_data/tushare_pro` 的 `value_kind=token` 和 `market_data/tickflow` 的 `value_kind=api_key` 使用，必须为 `http://` 或 `https://` URL。为空时分别使用数据源的默认入口；入口配置错误不会暴露密钥明文。
- TickFlow 使用 `value_kind=api_key`；测试会验证 `CN_Equity_A` 标的池 Quote、50 只批量 Quote 与 200 只批量五档深度。仅认证错误会标记 Key 为 `invalid`；403 权限不足、网络和短暂服务错误仅累计失败次数，便于购买权限后原 Key 直接重测。实时分钟线始终由 MooTDX 获取。
- Redis 连接串写入 `market_data/redis_cache` 的 `t_config_value`，`value_kind=redis_url`，使用 `CONFIG_MASTER_KEY` 加密；前端只展示 fingerprint，不返回明文 URL。
- Redis 的非敏感参数写入 `t_config_option`：`cache_backend`、`redis_key_prefix`、`redis_socket_timeout_seconds`、`data_asset_cache_enabled`、`data_asset_cache_ttl_seconds`、`default_cache_ttl_seconds`、`data_asset_summary_ttl_seconds`、`data_asset_daily_health_ttl_seconds`。
- Redis TTL 采用“数据中心默认 + 场景覆盖 + 未来兜底”规则：`data_asset_cache_ttl_seconds` 是数据中心缓存默认 TTL；数据中心资产总览优先读取 `data_asset_summary_ttl_seconds`；最近交易日完整性优先读取 `data_asset_daily_health_ttl_seconds`；`default_cache_ttl_seconds` 预留给后续实时/其他缓存族。
- `app.core.redis_client` 运行时优先读取配置中心 Redis 配置；配置中心未 seed、未启用或没有可用 `redis_url` 时回退 `.env`；Redis 不可用时回退进程内本地缓存。
- Notification 不使用敏感值池；`webhook_url`、`smtp_password`、`token` 直接作为渠道参数写入 `t_config_option`。
- 明文使用当前 `.env` 中的 `CONFIG_MASTER_KEY` 加密。
- API 和日志只返回 `fingerprint`，不返回明文或密文。
- 可用值必须满足 `is_enabled=true`、`status=active`，且不在 `cooldown_until` 冷却期内。
- 同一配置对象内按 `priority` 升序、`weight` 降序、`last_used_at` 空值优先排序。
- Search/Skill 的运行时环境变量名不再暴露给前端；问财、妙想、Kimi Search 只在子进程运行时内部注入兼容变量。

## API

配置中心挂载在 `/api/v1/config`：

- `GET /summary`
- `GET /items?category=search|llm|notification|market_data`
- `PATCH /items/{config_id}`
- `GET /items/{config_id}/options`
- `PUT /items/{config_id}/options`
- `GET /items/{config_id}/values`
- `POST /items/{config_id}/values`
- `PATCH /values/{value_id}`
- `POST /values/{value_id}/disable`
- `DELETE /values/{value_id}`
- `POST /values/{value_id}/test`
- `GET /migration/dry-run`

旧 `/tree`、`/nodes`、`/relations`、`/nodes/{id}/keys` 不再是配置中心 v2 API。

`market_data/tushare_pro` 的 `test` 不只校验密文能否解密：还会以 `600519.SH` 调用一次只读 `daily`，请求最近 10 个自然日的 `ts_code,trade_date,close`。Tushare 正常响应即通过，即使结果为 0 行；该测试仅代表日线连通性和 `daily` 权限，不代表其他接口权限已验证。

`market_data/tickflow` 的 `test` 会验证全市场标的池、50 只 Quote 和 200 只五档深度，并逐项记录行数、耗时和权限错误；测试完成后会关闭 SDK 客户端，且不读取或返回 API Key 明文。实时行情运行时没有通过上述能力的 active TickFlow Key 时会明确失败，避免悄然改用其他 Quote 数据源。

前端“系统设置中心 > 数据源 > Tushare Pro”在新增或编辑 Token 时提供“专属 API URL”；列表只显示专属入口或“使用默认 URL”，不会显示 Token 明文。

前端“系统设置中心 > 数据源 > TickFlow”使用 `api_key` 敏感值池，支持测试连接和可选的专属 API URL；页面明确标注它只提供实时 Quote，MooTDX 仍负责实时分钟线。

前端“系统设置中心 > 数据源 > Redis Cache”通过敏感值池新增 `redis_url`，例如 `redis://:password@host:6379/0`。测试 Redis 敏感值只执行一次 `PING`，返回连接可用性和耗时，不返回 URL 明文。

## 迁移

配置中心 v2 迁移脚本：

```bash
psql "$DATABASE_URL" -f docs/sql/08-config-center-v2-rebuild.sql
```

脚本做的事：

1. 创建 `t_system_config`、`t_config_value`、新版 `t_config_option` 和新版 `t_runtime_call_log`。
2. 从旧 `t_config_node/t_secret_key/t_config_option` 迁移 Search、LLM、Notification 配置资产。
3. 从旧 `provider/provider_key` 补迁 Search 和 LLM Key。
4. 校验 Search、LLM、Notification 固定配置对象和默认 LLM。
5. 校验旧阿里 Coding Plan Key 如果存在，则新表必须迁移成功。
6. 删除旧 `t_config_node/t_secret_key/t_config_relation` 和旧 options/log 备份表。

后续如仍需从旧 `provider_key` 增量迁移 Key，使用：

```bash
cd python-back
source .venv/bin/activate
python scripts/migrate_legacy_provider_keys.py --verify-decrypt --include-llm --apply
```

脚本会写入 `t_config_value`，不会输出明文。
