# 调度中心模块
<!-- wiki-migration -->

## 定位

`scheduler_center` 是 `stock-center` 的调度底座。它负责任务定义、任务触发、APScheduler 注册、运行日志和基础状态查询，不承载具体行情同步、策略扫描、通知发送等业务逻辑。

旧 `stock-analysis` 的调度模块可参考运行时设计，但不能照搬 `SchedulerApplicationService` 的业务耦合方式。新项目中，具体任务必须通过 `JobHandlerRegistry` 注册 handler 后才能执行。

## Runtime 规则

- `SCHEDULER_ENABLED=false` 为默认值，服务启动时不会自动注册任务。
- `SCHEDULER_ENABLED=true` 时，后端启动会尝试启动 APScheduler 并从数据库 reload 任务；如果数据库连接失败，FastAPI 仍继续启动，调度器关闭并在 `/api/v1/scheduler/status.error` 暴露错误摘要。
- `SCHEDULER_MAX_CONCURRENT_JOBS=2` 控制全局任务并发。
- 默认时区是 `Asia/Shanghai`。
- 第一阶段只支持五段 cron。
- `cron_expr=null` 表示仅手动运行。
- cron 星期语义按 crontab 处理：`1-5` 表示周一到周五，注册 APScheduler 前会转换，避免星期偏移。
- 任务配置页面固定使用 `Asia/Shanghai`，支持仅手动、每天、每周、每月 1-28 日和自定义五段 Cron；后端会在写库前校验 Cron，非法值返回 `invalid_cron_expr`。
- `timeout_seconds` 表示单次 handler 尝试的超时秒数；失败后最多按 `retry_count` 重试，并在每次尝试间等待 `retry_interval_seconds`。
- 默认 payload 与手动运行 payload 都按 `parameter_schema` 校验必填、类型、范围和枚举；schema 未定义的新字段会被拒绝，已有历史扩展字段可保留。
- 执行前使用 PostgreSQL advisory lock 做轻量防重复保护；拿不到锁时记录 `skipped/already_running`。
- 手动触发的异步任务由 `SchedulerRuntime` 持有当前进程内的 active task。前端可调用 `POST /runs/{run_id}/cancel` 请求终止；取消是协作式的，已经提交的批次数据保留，运行记录会尽量标记为 `cancelled/job_cancelled`。
- 后端启动时会清理上次进程退出遗留的 `running` 记录，将其标记为 `failed/scheduler_orphaned_after_restart`。这只修复运行日志状态，不回滚已经提交的业务数据。
- 任务完成后写入 `t_scheduler_job_run` 状态时，如果当前数据库连接已经被云库重启、恢复或网络中断关闭，调度中心会回滚当前 session，并用新 session 重试一次状态写入。这样可以避免“业务数据已经提交成功，但运行记录因为坏连接被误标失败”的情况。
- 任务执行会输出 `INFO` 级别日志：开始、重试、成功、跳过、关键 payload keys 和 affected rows。
- 业务模块必须输出自己的 `INFO/WARNING` 日志：长流程至少覆盖阶段开始、输入规模、批次完成、缺失数据摘要和最终行数。失败详情或关键缺失数量应进入 `t_scheduler_job_run.result_summary`，便于前端运行详情和日志共同排查。
- `t_scheduler_job_run.result_summary` 写入前会统一做 JSON-safe 编码；业务 handler 返回 Pydantic 结果时应使用 `model_dump(mode="json")`，避免 `date`、`datetime`、`Decimal` 等 Python 对象导致 JSONB 入库失败。

## API

所有接口都在：

```text
/api/v1/scheduler
```

主要能力：

- `/jobs`：查看、创建、更新、删除任务定义。
- `PATCH /jobs/{job_code}`：更新任务排期、启停、默认 payload、单次尝试超时和重试策略；更新成功后 API 自动 reload Scheduler。
- `/jobs/{job_code}/pause` 和 `/jobs/{job_code}/resume`：暂停或恢复任务。
- `/jobs/{job_code}/run`：手动触发任务。
- `/runs` 和 `/runs/{run_id}`：查询运行日志。
- `POST /runs/{run_id}/cancel`：终止当前进程内仍在运行的任务；如果运行记录为 `running` 但当前进程没有 active task，会标记为 `cancelled/job_cancelled_not_active`。
- `/status` 和 `/reload`：查看调度器状态和重新加载 cron。
- `/db-pool/status`：查看数据库连接池状态。

数据库连接诊断：

- `/api/v1/health` 只表示后端进程存活，不代表数据库可用。
- `/api/v1/health/db` 执行只读 `select 1`，返回 `ok/failed`、错误类型、错误摘要和连接池状态。
- `python-back/scripts/check_database_connection.py` 会用 `DATABASE_SSL=auto/disable/require` 三种模式探测当前 `DATABASE_URL`，输出脱敏连接目标和推荐排查方向。
- `DATABASE_CONNECT_TIMEOUT_SECONDS` 控制 asyncpg 连接超时；`DATABASE_SSL` 支持 `auto`、`disable`、`require`。

基础同步任务默认 `retry_count=0`，便于手动验证时快速暴露外部源失败；需要生产重试策略时再显式调整。`sync_trade_calendar` 默认同步当前年份，也可通过 payload 指定 `year` 和 `upsert/rebuild`；它沿用旧项目规则：周一到周五且 `chinese_calendar.is_workday(date)` 为真即开市，并补齐前后交易日。`sync_sector_catalog` 使用当前快照语义：只有单板块成分源确认完整时才物理删除缺失关联。其同花顺分页源由 Provider 内部逐页校验并重试，失败板块不写入部分结果。

`sync_stock_basic` 的状态口径固定为：沪深 Tushare `stock_basic.list_status=L/P/D` 分别对应 `active/suspended/delisted`；北交所/BJ/BSE 以及 `4/8/920` 代码段统一为 `excluded`，不进入股票池候选、`all_a_share` 动态范围和每日沉淀。AkShare/MooTDX fallback 只补充沪深 active 列表，不覆盖已有 `excluded/delisted/suspended` 状态。

`sync_index_catalog` 独立维护指数主数据，不与每日 `index_daily/index_dailybasic` 沉淀混在一起。它默认同步核心指数基础资料，并只对成分型指数同步当前成分股主数据。指数成分不保留历史快照；同步某指数时，本次完整结果中不存在的旧成分会被物理删除。Tushare 是主源；`index_weight` 默认按 `weight_lookback_months=3` 查询最近 3 个自然月，然后按 `trade_date` 分组取最新且满足预期成分数量的完整结果。AkShare fallback 只用于补充基础/成分，最终 canonical `index_code` 仍使用无后缀代码。成分型指数会校验预期成分数，fallback 去重后明显不足时跳过入库和删除。

`sync_tushare_a_share_topic` 与旧 `daily_market_close_ingest` 均已废弃并隐藏。日频量化沉淀拆为核心、增强、修复三段，避免一个任务暴露几十个开关。未来如果需要历史补数，单独设计 `backfill_*` 任务，不再把专题同步作为日常任务入口。

`daily_close_core_ingest` 默认 cron 为 `30 19 * * 1-5`，单次超时 6 小时、失败重试 1 次。它只处理收盘后稳定事实和基础因子，不等待晚间 Tushare 增强数据。核心指数日线执行 `Tushare index_daily -> AkShare stock_zh_index_daily_em -> MooTDX index` fallback，只写目标交易日 canonical 单事实。

`daily_close_enrichment_ingest` 默认 cron 为 `30 22 * * 1-5`，用于 `stk_factor_pro`、龙虎榜席位、市场统计、指数每日指标和板块资金流等晚到数据。增强事实落库后只重算受这些数据影响的增强因子，不重复沉淀日线和分钟线，也不涉及已废弃的 EOD quote。增强任务支持受控并发：`enrichment_block_concurrency` 控制独立增强块并发数。并发请求仍走 Tushare Token 池、专属 endpoint、共享限流和 Scheduler timeout；如果只有单 Token 且限频较低，并发不会突破官方频率，只能提升网络等待重叠和多 Token 利用率。`cyq_perf` 逐股批量沉淀耗时过长且当前价值不高，规划中移出每日增强任务，仅保留为个股详情按需查询候选能力。

`daily_close_repair_ingest` 默认 cron 为 `30 8 * * 1-5`，滚动修复最近 3 个交易日的增强缺口。它不全量重跑核心事实，只补晚到数据并按依赖重算因子；修复任务复用增强任务的并发参数。多日修复时，`top_list`、`index_dailybasic`、`daily_info`、`moneyflow_cnt_ths/moneyflow_ind_ths` 使用 Tushare 支持的 `start_date/end_date` 区间请求，第一轮统一落库区间事实，后续交易日只复用已落库事实并重算当日因子。`top_inst` 和 `stk_factor_pro` 仍按单日执行，避免遗漏席位明细或触发专业技术因子大结果集截断。`cyq_perf` 不参与修复任务。

历史回填不属于每日收盘沉淀。`docs/sql/55-data-asset-history-pipelines.sql` 将入口固定为个股、板块、指数各一条事实任务和一条因子任务，并删除旧的 7 条任务定义；`docs/sql/56-sector-history-range-backfill.sql` 将板块事实任务升级为逐板块区间请求和独立资金流窗口并发。推荐顺序是 `stock facts -> stock factors -> sector facts -> sector factors -> index facts -> index factors`；全部任务默认 disabled、手动先行、支持 `append_safe/rebuild`。完整参数、落表、依赖、并发依据、分钟数据边界和 smoke 步骤见 [[历史数据资产初始化]]。

`cyq_chips` 明细已从业务沉淀中移除；`t_stock_chip_distribution_daily` 由 `docs/sql/26-split-daily-close-ingest.sql` 删除。`cyq_perf` 也不再作为全市场批量沉淀来源，只保留为个股按需查询候选能力；历史已沉淀的 `t_stock_chip_perf_daily` 可作为实验数据保留。

## 第一阶段边界

- 不迁移旧项目 `scheduled_job` 里的具体业务任务。
- 前端调度任务页面支持编辑排期、执行策略和默认 payload；`parameter_schema` 驱动默认参数和手动运行表单，展示中文标签、说明、选项及数值范围。
- 不让调度模块直接 import 行情、LLM、Skill、通知等业务模块；这些模块各自提供 handler 并在应用启动时注册。
